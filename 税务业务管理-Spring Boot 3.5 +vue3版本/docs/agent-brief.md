## 2. UI 品质要求（不可忽略）

目标是成熟、克制、专业的企业/政务业务后台，不是营销落地页，也不是常见的
AI 渐变模板。 -
主背景用白色/浅暖灰，主内容为白色，正文用深灰，辅助文字用中性灰。 -
强调色选低饱和蓝灰或少量墨绿；成功/警告/错误用克制的状态色。 -
禁止大面积紫色/亮蓝渐变、荧光色、发光边框、过度阴影、玻璃拟态、无意义的彩色卡片堆叠。 -
使用统一 CSS 变量、间距系统、字体层级、圆角和边框规范。 -
页面布局采用侧边导航、顶部栏、面包屑、页面标题、筛选区、数据表格/表单等成熟后台结构。 -
列表页必须有合理筛选、重置、分页、加载态、空态、错误态。 -
表单要有字段标签、必填标识、校验反馈和清楚的保存/提交按钮。 -
状态不能只用颜色表达，必须同时有文本。 - 优先支持 1366×768 与 1440×900
桌面视口，并兼顾窄屏。 -
图表只展示有业务含义的数据，避免为了装饰堆图。 -
所有核心按钮必须真实工作；禁止无效按钮、死链接、仅展示不执行的假交互。 -
图标风格统一，不使用未经授权的品牌 Logo 或商业素材。 -
可借鉴信息架构与交互，不可整站照搬其他项目。

## 3. 技术栈

前端： - Vue 3 + TypeScript + Vite - Element Plus - Vue Router - Pinia -
Axios - ECharts - ESLint + Prettier

后端： - Java 17 - Spring Boot 3.5.x 兼容维护线，具体 patch
版本在实现时确认并锁定 - Spring Web - Spring Security - Jakarta
Validation - MyBatis-Plus Spring Boot 3 starter（或项目已采用 MyBatis
时保持一致，不要无理由替换） - MySQL 8.0 系列 - Flyway 数据库迁移 -
JUnit 5、Spring Boot Test、MockMvc - springdoc-openapi 可选但推荐

采用前后端分离的模块化单体，不使用微服务，不引入不必要的消息队列/分布式组件。API
前缀为 `/api/v1`。前端不得直接访问数据库。

## 4. 必须实现的九大模块

### 4.1 首页工作台

-   申报总量、待审核量、审核通过量、退回量。
-   近 6/12 个月申报趋势、状态分布、按类型统计的模拟金额。
-   待办列表、最近操作、常用入口。
-   指标必须来自后端真实数据，不能写死数字；无数据时显示空状态。
-   指标和图表遵守当前用户数据权限。

### 4.2 用户、角色和权限

-   登录、登出、当前用户信息、修改密码。
-   用户 CRUD（有关联数据时使用停用/软删除）。
-   角色管理、角色权限分配。
-   菜单权限、操作权限、API 权限分别处理。
-   Spring Security 在后端强制授权；不能只靠前端隐藏菜单或按钮。
-   未登录返回 401，无权限返回 403。
-   密码使用 BCrypt 等安全哈希；绝不明文存储或记录密码。
-   提供 ADMIN、CLERK、REVIEWER、ANALYST 等演示角色。

### 4.3 纳税人管理

-   仅使用虚构的模拟纳税人。
-   列表、详情、新增、编辑、启停、关联申报历史。
-   字段包括编号、名称、主体类型、虚构联系人/电话（可选）、状态、备注、创建/更新时间。
-   编号唯一；有申报历史的记录不得物理删除。

### 4.4 申报类型管理

-   模拟申报类型的新增、编辑、启停、查询。
-   类型绑定已发布的表单模板版本。
-   停用类型不得用于新建申报。
-   不得宣称模拟公式等于真实税法规则。

### 4.5 表单模板管理

-   模板列表、草稿编辑、字段配置、预览、发布、停用、版本历史。
-   字段类型至少支持文本、整数、金额/小数、日期、单选、多选、布尔。
-   支持必填、最大长度、数值范围、选项、帮助文字和排序。
-   发布后版本不可原位修改；修改必须产生新版本。
-   申报绑定提交时的模板版本，历史申报按原版本渲染。
-   不允许模板配置执行任意 JavaScript、SQL 或任意表达式。
-   V1 不要求复杂拖拽式表单设计器，先实现可靠的字段配置与预览。

### 4.6 申报管理

-   创建、保存草稿、编辑草稿、查看详情、提交、按规则撤回、退回后修改并重新提交。
-   状态：`DRAFT`、`PENDING_REVIEW`、`RETURNED`、`APPROVED`、`WITHDRAWN`。
-   申报编号由后端生成并唯一。
-   金额用 DECIMAL，不用 float/double。
-   后端校验必填项、类型、范围、模板版本、纳税人/申报类型状态和重复申报规则。
-   已提交记录不可由经办人直接修改；已通过记录不可直接编辑。
-   防止重复提交，使用事务、业务校验和数据库约束兜底。

### 4.7 审核管理

-   待审核列表、审核详情、通过、退回、审核意见、审核历史。
-   只有授权 REVIEWER 可审核；经办人不能审核自己的申报。
-   只能处理 `PENDING_REVIEW` 状态。
-   退回原因必填。
-   审核状态变更与审核历史写入同一事务。
-   重复审核/并发审核应失败并返回 409，不得产生两条互相冲突的结果。

### 4.8 统计分析

-   申报数量、待审核、通过、退回、模拟金额、审核通过率。
-   按月份、申报类型、状态和主体类型统计。
-   统计口径必须写在图表标题或说明中。
-   统计接口执行服务端聚合，遵守权限。
-   提供空数据、加载和错误状态。

### 4.9 综合查询、系统设置和审计

-   组合查询、分页、白名单排序、重置条件、详情。
-   条件包括申报编号、纳税人编号/名称、类型、状态、申报期间、提交时间范围、经办人/审核人（按权限）。
-   CSV
    导出作为第一阶段导出格式；导出受权限、筛选条件和条数限制，并记录日志。
-   字典和模拟期限配置可做基础实现。
-   操作日志记录用户、动作、对象、结果、时间、traceId；禁止记录密码、Token
    或完整敏感载荷。
-   日志不得由普通 UI 修改。

## 5. 数据库最低要求

必须设计并提供版本化迁移 SQL，至少包含： - `sys_user` - `sys_role` -
`sys_permission` - `sys_user_role` - `sys_role_permission` -
`taxpayer` - `declaration_type` - `form_template` - `form_field` -
`tax_declaration` - `declaration_review` - `sys_operation_log` - 可选
`sys_dict`

基本关系： - 用户---角色多对多。 - 角色---权限多对多。 -
纳税人---申报一对多。 - 申报类型---模板一对多。 - 模板---字段一对多。 -
申报---审核历史一对多。

通用约束： - MySQL InnoDB、utf8mb4。 -
主键、唯一约束、必要索引、创建/更新时间。 - 金额使用 `DECIMAL(18,2)`。 -
`tax_declaration` 保留用于查询的稳定字段和模板版本快照；动态表单数据可存
JSON。 - 历史申报保留纳税人名称、申报类型名称和模板版本快照。 -
业务表不能随意硬删除。 -
种子数据只能是虚构数据，演示账号密码不得复用真实密码。 - 提供 ER
图（Mermaid 或其他可维护格式）及 `docs/database-design.md`。

## 6. 代码结构和工程质量

推荐后端包按业务模块拆分：`auth`、`user`、`role`、`taxpayer`、`declarationtype`、`formtemplate`、`declaration`、`review`、`statistics`、`audit`、`common`、`config`、`security`。
每个模块按 Controller、Service、Mapper、DTO、Entity/DO、VO
等职责分层。 - Controller 不承载复杂业务。 - Service
集中实现状态机、事务和业务校验。 - 不直接把 Entity 当作 API
请求/响应对象。 - 统一响应、统一异常、统一分页。 - 数据库变更通过 Flyway
或等效迁移脚本。 - 不把密钥、数据库密码提交到 Git。 - 提供
`.env.example`，不要提交实际 `.env`。 - README
写明版本、配置、数据库初始化、前后端启动、演示账号、重置数据和常见故障。 -
生成 `docs/api-spec.md`、`docs/test-plan.md`、`docs/changelog.md`。

返回 403。 3. 重复纳税人编号创建失败。 4. 草稿保存成功并能重新读取。 5.

已处理申报不能重复审核，返回合理冲突。 12.
统计数据与相同筛选条件的业务数据一致。 13. 分页和组合筛选正确。 14.
导出遵守筛选条件和权限。 15. 日志不包含密码和 Token。
