# UI 参考调研记录

- 调研日期：2026-10-29
- 调研人：项目开发者
- 调研目的：为“税务业务管理系统”确定信息架构、列表/表单/审核页面模式与可访问性基线，避免凭空设计。
- 调研方式：通过 `curl` 抓取公开页面 HTML，并人工阅读正文与设计说明；未使用第三方截图作为项目素材。

> 说明：以下“观察”只记录本次实际抓取到的文字与结构；抓取失败的来源单独列在“失败记录”，未把搜索结果摘要当作已访问页面。

## 1. 参考来源

### 1.1 程聚宝：税务 SaaS 平台案例

- URL：https://devlg.com/caseinfo/15354
- 页面标题：`税务SaaS平台_软件定制-程聚宝`
- 访问日期：2026-10-29
- 访问结果：成功获取 HTML 与正文。

实际观察到的业务与交互要点：

1. 业务范围覆盖增值税、印花税、个人所得税、企业所得税等多税种，说明税务系统需要“税种/申报类型”这一层主数据，而不是把所有申报做成同一张表。
2. 页面描述“报税员录入 → 审核员审核 → 报税”的分工，佐证了本项目的“申报人提交、审核人审核”角色分离与状态机设计。
3. 页面提到自动计算、一键申报、RPA 报税、报表回捞、客户与账号管理。本项目不接入真实税局接口，但保留“自动汇总金额、状态跟踪、操作留痕”的产品思路。
4. 页面强调多客户/多账号管理，对应本项目的纳税人档案与按纳税人检索。

未从该页面获取的内容：具体页面布局、配色、组件尺寸。该页是案例介绍页，不是可交互产品，因此不据此声称“参考了其界面”。

对本项目的影响：

- 侧边栏按“工作台 / 申报业务 / 审核 / 统计分析 / 系统管理”分组，而不是按数据库表平铺。
- 申报列表必须让录入人一眼看到状态（草稿、待审核、已退回、已通过、已撤回），审核列表只呈现待办。
- 审核详情页同时给出申报数据与审核历史，避免审核人来回跳转。

### 1.2 明道云 / 普华永道：智慧税务系统案例

- URL：https://www.mingdao.com/case/126
- 页面标题：`普华永道携手明道云打造智慧税务系统`
- 访问日期：2026-10-29
- 访问结果：成功获取 HTML 与正文。

实际观察到的要点：

1. 案例强调税务工作流的“自动流转、自动审批、自动填报”，以及与企业现有工作台（如钉钉/企业微信）集成。
2. 案例把“标准化”列为主要挑战，说明税务申报系统需要模板化字段、统一状态与统一审核意见，而不是自由文本表单。
3. 案例呈现的是零代码平台能力，本项目不采用其技术栈，只借鉴“流程状态可视、待办集中、模板标准化”的产品原则。

对本项目的影响：

- 表单模板 + 字段定义 + 版本快照，保证同一税种多次申报的数据结构一致。
- 待审核数量直接显示在工作台，审核入口固定。
- 审核动作必须填写意见（退回时必填），形成可追溯的审核历史。

### 1.3 GOV.UK Design System：Check answers

- URL：https://design-system.service.gov.uk/patterns/check-answers/
- 访问日期：2026-10-29
- 访问结果：成功获取页面。

实际观察到的模式：

1. 提交前提供“检查答案”页，用摘要列表（summary list）逐项展示用户输入。
2. 每个可修改项旁有明确的 “Change” 链接，并为链接补充视觉隐藏的字段名，保证读屏用户能区分多个 “Change”。
3. 该模式的目标是让用户在最终提交前确认关键信息，降低误提交。

对本项目的影响：

- 申报详情页采用“摘要列表”展示纳税人、申报类型、所属期、金额、模板版本。
- 草稿详情页提供“编辑”入口；已提交后隐藏编辑入口，只保留撤回/查看。
- 审核页在通过/退回按钮上方再次展示关键字段，减少误操作。

### 1.4 GOV.UK Design System：Error summary

- URL：https://design-system.service.gov.uk/components/error-summary/
- 访问日期：2026-10-29
- 访问结果：成功获取页面。

实际观察到的规则：

1. 校验失败时页面顶部必须出现错误摘要，即使只有一个错误。
2. 错误摘要标题使用 “There is a problem”，并把焦点移动到摘要区域。
3. 摘要中的错误文案与字段旁的内联错误保持一致。
4. 页面 `<title>` 增加 “Error:” 前缀，便于多标签页辨认。
5. 摘要中的每条错误链接到对应字段。

本项目的落地情况（如实说明）：

- 已实现：顶部 `role="alert"` 错误提示、字段旁内联错误、错误文案与字段错误同源（`ValidationException.getFieldErrors()`）。
- 已实现：表单提交失败后回显用户输入，不清空表单。
- 未完全实现：错误摘要的“点击锚点跳转字段”和自动聚焦。当前 6 个表单页使用顶部提示 + 字段内联错误，未生成带锚点的错误列表。这是后续可改进项，不在文档中伪称已实现。

### 1.5 Bootstrap 5.3：Navbar

- URL：https://getbootstrap.com/docs/5.3/components/navbar/
- 访问日期：2026-10-29
- 访问结果：成功获取页面。

实际观察到的模式：

1. 响应式导航在窄屏折叠，通过 toggler 展开。
2. 当前页使用 `aria-current="page"` 标记，而不是只靠颜色。
3. 导航项支持品牌区、主链接区、右侧用户区三段式布局。

对本项目的影响：

- 顶部栏：品牌/系统名 + 当前用户 + 退出按钮。
- 左侧栏：分组菜单；当前菜单通过服务端 `activeMenu` 变量加 `active` 类，并输出 `aria-current="page"`。
- 窄屏下侧边栏通过按钮开合，主内容保持可读。

### 1.6 Bootstrap 5.3：Tables（辅助参考）

- URL：https://getbootstrap.com/docs/5.3/content/tables/
- 访问日期：2026-10-29
- 访问结果：成功获取页面。

采用的约定：

- 列表使用紧凑表格 + 表头浅色底，操作列右对齐。
- 数字列右对齐，状态用徽标而非纯文字颜色。
- 空列表给出明确空状态文案，不显示“假数据”。

## 3. 设计决策汇总

| 决策 | 依据 | 实现位置 |
| --- | --- | --- |
| 左侧分组导航 + 顶部用户区 | 税务 SaaS 多模块、角色差异大 | `WEB-INF/views/common/header.jspf`、`sidebar.jspf` |
| 当前菜单服务端标记 | Bootstrap `aria-current` 约定 | `activeMenu` + JSP 条件类 |
| 列表页统一“筛选区 + 表格 + 分页” | 税务局/企业均需按状态、税种、期间检索 | `common/pagination.jspf`、各列表 JSP |
| 状态徽标 | 状态是申报流转的核心信息 | `assets/css/views.css` 状态类 |
| 详情页摘要列表 | GOV.UK Check answers | `declarations/detail.jsp`、`reviews/detail.jsp` |
| 提交前确认、审核二次确认 | 防止误提交/误审核 | `data-confirm` / `data-confirm-button` |
| 表单错误顶部提示 + 字段内联 | GOV.UK Error summary 的核心目标 | `common/messages.jspf`、各表单 JSP |
| 窄屏侧栏折叠 | Bootstrap Navbar 响应式思路 | `assets/js/app.js`、`views.css` |
| 数字右对齐、金额千分位 | 税务表格可读性 | JSTL `fmt:formatNumber` |
| 不使用渐变/大图/动画 | 业务系统以密度和清晰度为先 | `views.css` |

## 4. 视觉基线

- 主色：`#1f4e79`（深蓝，用于侧栏与主按钮），辅助色 `#2f6f5e`（税务绿，用于成功态）。
- 背景：`#f4f6f8`；卡片白底、1px 边框、4px 圆角，不使用重阴影。
- 字体：系统字体栈（`"Segoe UI", "Microsoft YaHei", sans-serif`），正文 14px，表格 13–14px。
- 状态色：草稿灰、待审核橙、已退回红、已通过绿、已撤回深灰；均配合文字标签，不只依赖颜色。
- 表格：表头 `#eef2f6`，行悬停浅蓝，操作列固定右对齐。
- 焦点：保留浏览器默认焦点环，额外为按钮/链接增加 `:focus-visible` 轮廓，保证键盘可用。

## 5. 结论

本项目界面不是对某一产品的复刻，而是把上述可验证的模式落到传统 JSP 页面：

- 信息架构来自税务业务角色分工与多税种现实。
- 详情/审核页的“摘要 + 明确动作”来自 GOV.UK 的检查答案模式。
- 响应式与可访问性基线来自 Bootstrap 5.3 文档。
- 未实现的模式（错误摘要锚点跳转、自动聚焦）已明确标注，避免夸大。
